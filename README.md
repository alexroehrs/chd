# Chained Health Data (CHD)

Patient-controlled sharing of encrypted **HL7 FHIR R4** records on a permissioned
**Hyperledger Besu** network with **QBFT** consensus.

CHD keeps clinical content **off-chain and encrypted on the client**. The ledger stores only
what is needed to prove consent, integrity and access:

| On-chain (`CHDRegistry`)                         | Off-chain (gateway)                          | Client only                     |
|--------------------------------------------------|----------------------------------------------|---------------------------------|
| record owner and SHA-256 digest of the envelope  | AES-256-GCM encrypted envelope               | plaintext FHIR Bundle           |
| time-bound, revocable grants                     | data key wrapped per reader (X25519 + HKDF)  | private keys (secp256k1, X25519)|
| X25519 public-key directory, institution list    | request log (hashes of signed requests)      | unwrapped data keys             |
| audit, revocation and erasure events             |                                              |                                 |

Erasure uses **crypto-shredding**: `eraseRecord` sets an on-chain flag, after which the gateway
deletes the ciphertext and every wrapped key (on the owner's `DELETE` request, or on the next
access attempt to the record), so no key able to decrypt the record remains in the system.

This repository accompanies the article *Chained Health Data: Patient-Controlled Sharing of
Encrypted HL7 FHIR Records on a Permissioned QBFT Blockchain* (submitted to the Journal of
Internet Services and Applications).

## Repository layout

```
contracts/      CHDRegistry.sol (the system) and OnChainBaseline.sol (encrypted records stored on-chain, for comparison)
src/            client SDK, gateway, envelope encryption, signed requests, FHIR validation
network/        scripts to generate and run a 4-validator Besu QBFT network (local binaries or Docker)
test/           20 automated tests (6 offline crypto tests + 14 end-to-end tests against the Besu network)
bench/          benchmark harness, synthetic FHIR generator, figure and table scripts
results/        raw results (JSON) and the test log used in the article
scripts/        compile, deploy and demo
```

## Requirements

* Node.js 22 or newer
* Either **Docker**, or **Java 25** plus the **Hyperledger Besu 26.9.0** binary distribution
  (`https://github.com/besu-eth/besu/releases`)
* Python 3 with `matplotlib` for the figures (`pip install matplotlib`)

## Quick start

```bash
npm install
npm run compile                      # solc-js 0.8.37, no native compiler needed

# --- network with local binaries ---
export BESU=/path/to/besu-26.9.0/bin/besu   # and JAVA_HOME pointing to a Java 25 JDK
npm run network:setup                # keys + genesis (BLOCK_PERIOD=2 by default)
npm run network:start                # node1 RPC at http://127.0.0.1:8545
# --- or with Docker (keys and genesis are still generated by setup.sh) ---
# BESU="docker run --rm -u $(id -u) -v $PWD/network:$PWD/network hyperledger/besu:26.9.0" npm run network:setup
# chmod -R a+rwX network/data        # the besu image runs as uid 1000 and must write there
# docker compose -f network/generated/docker-compose.yml up -d

npm test                             # 20 tests against the running network
npm run demo                         # end-to-end walk-through
npm run network:stop
```

To run the gateway as a standalone service: `npm run deploy` writes `deployment.json`
(registry address and a development admin key; gitignored), then `npm run gateway` serves it
on `PORT` (default 8080) with storage in `DATA_DIR` (default `gateway-data/`). All scripts
read the RPC endpoint from `RPC_URL` (default `http://127.0.0.1:8545`); `deploy` accepts an
`ADMIN_KEY`.

## Reproducing the experiments

The results in the article come from the following runs, in this order, on a network with a
2 s block period (`BLOCK_PERIOD=2 npm run network:setup && npm run network:start`):

```bash
node bench/run-bench.mjs crypto  --label p2s --reps 50
node bench/run-bench.mjs gas     --label p2s
node bench/run-bench.mjs latency --label p2s --reps 30
node bench/run-bench.mjs load    --label p2s --levels 1,4,16,64 --duration 60 --warmup 10
node bench/run-bench.mjs load    --label p2s --name load-write-high --workloads write --levels 128,256 --duration 60 --warmup 10
```

and, for the block-period sensitivity analysis, on fresh networks generated with
`BLOCK_PERIOD=1` and `BLOCK_PERIOD=5`:

```bash
node bench/run-bench.mjs latency --label p1s --reps 20
node bench/run-bench.mjs load    --label p1s --name load-write --workloads write --levels 16,64 --duration 60 --warmup 10
node bench/run-bench.mjs latency --label p5s --reps 20
node bench/run-bench.mjs load    --label p5s --name load-write --workloads write --levels 16,64 --duration 60 --warmup 10
```

Each run writes `results/<label>/<name>.json` with the host and network metadata. The figures
and the result tables of the article are then produced with

```bash
python3 bench/plot.py p2s figures                 # gas.pdf, crypto.pdf, load.pdf
python3 bench/fill_tables.py path/to/main.tex     # fills the latency, load and block-period tables
```

The test log in `results/p2s/tests.log` was produced with `npm test > results/p2s/tests.log 2>&1`.
All options of the harness are listed at the top of `bench/run-bench.mjs`.

## Security model (summary)

* Requests to the gateway are signed with the requester's Ethereum key (EIP-191) over method,
  request path, body digest, timestamp and nonce; requests whose timestamp differs from the
  gateway clock by more than 60 s, and replayed (address, nonce) pairs, are refused.
* The gateway authorizes every read with `hasAccess` on the ledger, so revocation and expiry
  take effect at the next block.
* Uploads are accepted only from the on-chain owner and only if the envelope digest equals the
  on-chain digest; readers verify the digest again before decrypting.
* The gateway is honest-but-curious: it only ever holds ciphertext and wrapped keys. It serves
  plain HTTP and has no rate limiting; a deployment needs TLS and rate limiting in front of it.
* Accounts are pseudonyms. The ledger still reveals how many records an account owns and which
  institutions were granted or logged access, and when.
* Clients and the gateway read ledger state from one node; a node that misreports state is not
  detected by the current implementation.

The system is a research artifact. Before any real use it needs, at least, key recovery for
patients, a replicated gateway with a shared nonce store, a consortium governance contract
instead of a single admin key, and a legal assessment.

## Data

All data used in tests and experiments is **synthetic**, produced by `bench/fhir-gen.mjs`.
No real patient data is included or required.
